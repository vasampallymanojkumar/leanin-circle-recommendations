# Circle recommendation API — technical design

**Goal.** Help members discover relevant, active communities with room to join, with understandable reasons. A Python standard-library HTTP API serves normalized SQLite data. No runtime model, paid dependency, or network access is needed. The supplied JSON remains the source of truth and seeds a disposable database at startup.

**Retrieval and ranking.** SQL excludes existing memberships, unlisted groups, and Circles at capacity using the supplied member-count aggregate. Python excludes activity older than 90 days or in the future. Stated topic interests dominate ranking; primary topics carry more weight than secondary tags. Without stated interests, existing membership topics provide a weaker signal. Fully cold-start users receive active groups across topics. Recency and log-saturated feed/chat volume add a bounded health signal so size and message volume cannot dominate relevance. Scores are deterministic, ties use ID, and explanations cite only observed signals. Request-to-join groups stay eligible with accurate copy.

**Diversity.** Greedy selection keeps one Circle per primary topic. This handles the planted negotiation duplicates and broadens discovery; it deliberately may return fewer than the requested limit. It can suppress useful distinct communities on the same topic and cannot recognize semantically duplicate groups with different or missing topics. Production should compare richer group attributes and validate the diversity/relevance balance with members.

**Schema and indexes.** `users` and `circles` retain supplied scalar profiles; `topics` is the taxonomy. Composite-key `user_interests` and `circle_tags` normalize arrays and eliminate repeated tags. `memberships(user_id,circle_id)` supports fast exclusion and stores leader roles; the reverse index supports Circle member/leader reads. `activity` retains supplied posts, with a composite foreign key ensuring authors belong to the Circle and an index on `(circle_id,created_at)`. Interest-by-topic, Circle-topic, and visibility/freshness indexes support future candidate retrieval. Foreign keys protect relationships; checks constrain capacity, profile completeness, and enums. Activity is retained for future richer analysis, but current ranking uses aggregates to avoid double-counting feed events. The current small scan does not exploit every index.

**Time and tradeoffs.** The explicit default date, 2026-09-21 UTC, keeps frozen-data evaluation reproducible; `--as-of` supports other dates. Historical 30-day counts remain fixed, so a live service must refresh them. We use `member_count` rather than deriving occupancy from the partial membership export. Thresholds and weights are transparent heuristics, not empirically validated. No location match is attempted because Circles lack structured location; users see format. Photos, completeness, names, and sensitive identity guesses do not affect rank. No LLM call, embeddings, collaborative filtering, or engagement-based optimization is required for this scope.

**Validation and production.** Tests cover all 100 members, four planted scenarios, availability/privacy exclusions, duplicates, explanations, nulls, deterministic output, database integrity, and HTTP error contracts. For production: replace the development server with a deployed framework, authenticate callers and authorize user access, rate-limit requests, use PostgreSQL and bounded indexed candidate retrieval, refresh aggregates asynchronously, and cache candidates with membership/capacity invalidation. Returned availability is advisory; joining must check capacity atomically. Track impressions, requests, successful joins, sustained participation, latency, and empty-result rates; audit visibility, fairness, and popularity concentration. Evaluate weights and topic diversity using member feedback and offline relevance sets before experimentation. Database startup must migrate rather than reseed production data.
